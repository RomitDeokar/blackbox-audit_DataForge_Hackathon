The acceptance test: 606 real trials

Interrupt the confirmation at every offset from −500 ms to +500 ms in 10 ms steps, three runs each — 303 trials per variant. Each trial writes to the real store and is graded against an independent oracle computed straight from the Rime timestamps, never from the fence itself. Runs offline in about a second and makes zero API calls.

Why the real LiveKit path breaks on mobile — and what this demo replaces

from docs/MOBILE_SETUP.md
It is not a Rime problem. Rime runs inside the agent worker; the phone never talks to Rime directly. What breaks on mobile is the LiveKit client path — and when that breaks the agent never hears you, so it never speaks, so it looks like TTS is broken.
This demo sidesteps all six. There is no WebRTC leg and no provider key: the phone talks plain HTTPS to this server and speaks through its own on-device synthesiser, paced by the cached Rime word timeline. The fencing decision is unchanged, so the thing being demonstrated is still the real thing.

How it works

The claim: a voice agent that gates database writes behind confirmed audio playback — not just LLM tool-call completion — will never commit a state change the caller did not actually hear, even under hundreds of rapid mid-sentence interruptions. A naively implemented agent will.

Why the offset is keyed to the timestamp stream

“Cancel 120 ms after the word ‘confirmed’ finished playing” is a statement about the caller’s ear. “Cancel 2.4 s after the tool call” is a statement about a network, a jitter buffer and an event loop — it would smear the measurement across ~100 ms of noise, wider than the effect being measured. Every barge-in in this demo and in the sweep is therefore scheduled off gating_word_end + offset_ms.
